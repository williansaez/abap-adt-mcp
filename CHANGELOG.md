## [1.0.1] - 2026-09-04 - Certificate verification cannot be switched off for every destination at once
Security and reliability of the TLS decision. Verification was already the default for a destination that configures nothing, but that default could be revoked from outside the configuration, silently and for everything at once.
- `NODE_TLS_REJECT_UNAUTHORIZED=0` is deleted from the environment before the first connection (`enforceTlsVerification()` in `src/lib/tls.ts`, called when `src/index.ts` loads) and the server reports on stderr that it was ignored. Node reads the variable at connection time, so it reached every outbound connection of the process, including destinations that never asked for it and the `fetch` calls in `src/lib/oauth.ts` and `src/lib/apiReleases.ts` that no destination agent covers. Warning about it on stderr was not enough for a server that speaks over stdio, where nobody reads stderr.
- `buildHttpsAgent()` always returns an agent, and the agent states `rejectUnauthorized` instead of inheriting Node's default: `false` only under `insecureTls`. An explicit value wins over the environment variable, so the decision to verify travels with the destination rather than with the environment the server happens to run in. `CookieHttpClient` applies the same rule to the agent it builds when none is passed.
- Turning verification off is still possible and still per destination (`insecureTls`), which means the choice has to name the system it applies to. Behaviour change: a setup that relied on `NODE_TLS_REJECT_UNAUTHORIZED=0` now fails, with a startup message pointing at the destination-level option.
- Consequence of the always-present agent: each destination owns its connection pool, with `keepAlive: true`, destroyed with the destination. On Node 18, whose global agent does not keep connections alive, this removes a TLS handshake per request.
- Documentation corrected wherever it described the variable as merely discouraged: README, SECURITY.md, docs/CONFIGURATION.md, docs/TROUBLESHOOTING.md, docs/ARCHITECTURE.md. SECURITY.md no longer offers it as a way to reach an OAuth token endpoint behind a corporate CA; `NODE_EXTRA_CA_CERTS` is the mechanism for that.

## [2.0.0] - 2026-09-08 - Node 22 floor, puppeteer-core 25, Dependabot cooldown, TLS by name
Breaking: the minimum Node version rises from 18 to 22.12.0. Node 18 and 20 are past end of life and receive no security fixes; a server holding SAP credentials should not run on them.

Its `@puppeteer/browsers` 3 replaces `extract-zip` with `modern-tar`, which removes the last open Dependabot alert (GHSA-jmr9-qjv8-65gv, CVSS 8.1, no patched version exists; issue #16) from the dependency tree instead of arguing about reachability. The vulnerable path (unpacking a downloaded browser archive) was never taken here: the server drives a browser already installed on the machine. `npm audit` reports zero vulnerabilities and the lock file loses 615 lines.
- `engines.node` is `>=22.12.0`, the floor `puppeteer-core` 25 sets. CI runs on Node 22 and 24. The container image was already `node:22-alpine`.
- `browserLogin.ts` uses `page.createCDPSession()`; `page.target()` is deprecated in puppeteer 25. The lazy dynamic import stays, now for install weight rather than for `require()` compatibility.

- Dependabot (`.github/dependabot.yml`): cooldown before any proposal (3/7/30 days for patch/minor/major, 7 for actions and images), security updates grouped into one pull request instead of one per transitive package, GitHub Actions grouped into one monthly pull request, a `docker` entry for the `node:22-alpine` base image, and major versions of `puppeteer-core`, `@types/node` and the base image excluded from automation because each can move the Node floor. SECURITY.md describes the same rules.
- GitHub Actions bumped in one go, superseding Dependabot's four separate pull requests (#2 to #5): `actions/checkout` v7, `actions/setup-node` v7, `docker/login-action` v4, `docker/build-push-action` v7. All four run on the Node 24 action runtime; no workflow uses `pull_request_target`, so the checkout v6 default change does not apply here.
- `tls.servername` on a destination (#13): the name the certificate is verified against and sent as SNI, for systems reached by IP address or short hostname whose certificate carries the fully qualified name. Verification stays on; `insecureTls` is no longer the only way through that landscape. Same agent for basic, OAuth and SSO API calls; `listSystems` shows `servername NAME`. Covered by a test that runs a self-signed server on 127.0.0.1 (certificate minted at test time with `openssl`, skipped where it is absent): fails on the name with the right CA alone, passes with `servername`, still fails on the issuer without the CA.
- New error kind `tlsCertificate` (#14): a handshake failure used to reach the model as a bare Node code. The hint now names the destination and the fix: unknown issuer gives the `openssl s_client` line with that destination's host and port and points at `tls.ca`; a name mismatch quotes the names Node reported and points at `tls.servername`; an expired certificate says that only renewal fixes it. `insecureTls` is mentioned last, described as verification off for that destination. Detected from the Node code on the error or the wrapped axios error, or from the message text a handler rethrows, and checked before any status-based rule since a handshake has no HTTP status. `classifyAdtError` takes an optional context (`destination`, `url`) that the tool-call handler now supplies.
- `insecureTls` stays (#15): SECURITY.md records the decision. With `tls.ca`, `tls.servername` and the `tlsCertificate` hints in place, what remains for the flag is an expired or unfixable certificate on a sandbox; refusing that would push people to a global bypass outside the server. Off by default, per destination, announced at startup, visible in `listSystems`, mentioned last in every hint. The two CodeQL `js/disabling-certificate-validation` findings closed as fixed with the 1.0.1 agent change. SECURITY.md's residual-risks list also stopped claiming there is no Dependabot.
- Dev tooling: `jest` 30, `ts-jest` 29.4, `typescript` 6.0, `@types/jest` 30, replacing Dependabot's #23 whose lock file lacked `jest-util`. TypeScript 6 defaults `types` to `[]`, so `ts-jest`, which reads `tsconfig.json`, lost the jest globals; `jest.config.js` now hands it `tsconfig.test.json`, which names `jest` and `node`. TypeScript 7 (the native compiler) waits for a `ts-jest` that accepts it; the dev-tooling group ignores that major until then.
- `dotenv` is loaded with `quiet: true`. Version 17 prints an "injected env" line to stdout by default, and in stdio mode stdout is the JSON-RPC channel; a `.env` next to `package.json` would have broken every host. `dotenv` moves to 16.6.1, the first 16 that types the option.
- `@types/diff` removed: `diff` 9 ships its own type definitions and the package is a stub. `@types/node` updated within the 22 line (22.20.1); the 26 that Dependabot proposed (#6) is refused by the new ignore rule because the types must not run ahead of `engines.node`.

## [2.0.1] - 2026-09-08 - First-login traps, policy holes, re-auth on the real error, one-line ENDMETHOD
Fixes from a three-team validation of 2.0.0 (docs, src, packaging), each verified against the code before it was fixed.
- `allowedTransports` now reaches `renameExecute`, `extractMethodExecute` and `changePackageExecute`: the transport travels inside the `refactoring` proposal returned by the preview step, which the gate never read, so a destination bounded to `DEVK9*` could execute a rename recorded on any transport. The proposal's `transport` and every `affectedObjects[].transport` are checked; a proposal without one is refused (closed mode). `refactoringTransports()` in `src/lib/policy.ts`, unit tests added.
- `deniedTools` accepts `toolset:<name>` (`toolset:git`, `toolset:rap*`) besides names and globs. The example `["transportRelease", "git*"]`, repeated in the policy header, three READMEs, AUTH.md, CONFIGURATION.md and the tool notes, left `pushRepo`, `stageRepo`, `checkRepo`, `remoteRepoInfo` and `switchRepoBranch` callable, and `pushRepo` sends ABAP source to an external remote. Every example now says `toolset:git`; `git*` keeps working for the tools it did match.
- Errors are classified on the SAP error, not on the wrapper text. Handlers rethrow `McpError("<what failed>: <message>")` with the original error attached as `cause` (`BaseHandler.adtFailure`, 157 call sites), and `classifyAdtError` classifies the cause first, so the HTTP status and code survive the wrapping. The session-expired and stale-lock text rules are stricter (`SAMLRequest`, "saml login/response/assertion", "invalid lockhandle"): an ordinary not-found error for `ZCL_SAML_HANDLER` or `GET_LOCKHANDLE` no longer triggers re-authentication, a lock-ledger wipe and a browser window.
- Release guards: `release.yml` runs only for final tags `vX.Y.Z`, refuses a tag whose commit is not an ancestor of `main`, checks the tag against every version file with `scripts/check-versions.js` (`npm run version:check`, also in CI), and publishes npm and GHCR from two separate jobs after one verify job; the npm publish is skipped when that version already exists, so a re-run cannot fail half way. Before, any `v*` tag became npm `latest` and the `:latest` image with no ancestry check.
- The Claude Code plugin manifest pins `npx -y abap-adt-mcp@<version>` instead of running whatever npm serves as latest at the host's next start; the pin is part of the version check and moves with each release.
- `.gitignore` no longer lists the tracked `package-lock.json`, and ignores `coverage/`, `.env.*` (except `.env.example`) and `*.tgz`.
- `setMethodSource` and `getMethodSource` handle `METHOD x. ENDMETHOD.` on one line as a complete block (a trailing `"` comment is ignored), and a block whose ENDMETHOD is missing before the next METHOD header is reported with the line of that header and refused for writing instead of being replaced together with the following method.
- Legacy single-system setup (`SAP_URL`): when `SAP_AUTH_TYPE` is unset the auth mode is inferred from the credentials present, `basic` from `SAP_USER` and `SAP_PASSWORD`, `oauth` from `SAP_OAUTH_TOKEN_URL`, `SAP_OAUTH_CLIENT_ID` and `SAP_OAUTH_CLIENT_SECRET`, and the inference is reported on stderr. Credentials an explicit mode will not use are reported as unused, and an unknown `SAP_AUTH_TYPE` value says so. Before, `.env.example` and docs/AUTH.md showed a password setup without `SAP_AUTH_TYPE=basic`, which loaded as `sso`: the first call opened a browser against the on-prem host and waited 300 s. Both templates now carry `SAP_AUTH_TYPE=basic`. `systems.json` entries are unchanged: the per-entry default stays `sso`, write `authType` explicitly.
- Browser SSO matched harvested cookies against the URL host including its port, so a destination such as `https://sap.example.com:44300` never saw a session cookie and every login timed out. Cookies are now matched against the hostname (`src/lib/browserLogin.ts`), with unit tests; the per-host profile directory keeps the host-with-port name, so existing profiles are reused.

## [2.1.0] - 2026-09-15 - Headless logon without a browser, and the cookie jar stays on its own origin
The on-premise gap 2.0.x left open: a named user who authenticates through SNC, has no stored SAP password and no unattended OAuth client, and cannot reach an ADT URL in a browser. Contributed by João Gementi (#45), with two follow-ups from its review (#46).
- New `authType: "sso2"`: an opt-in headless mode that asks a trusted local program for a short-lived SAP logon ticket and keeps it in the in-memory cookie jar only. The program is named by an absolute path and run through `execFile` with `shell: false`, arguments stay separate strings, output and run time are bounded, and its stdout and stderr are never copied into an MCP error or the audit log. The ticket is validated against the RFC 6265 cookie-octet set and refused rather than rewritten, because rewriting a signed ticket invalidates it. The repository deliberately ships no provider binary and does not link the SAP NW RFC SDK: each installation supplies and reviews its own bridge. Configure it as `sso2: { command, args, timeoutMs }` per destination, or `SAP_SSO2_COMMAND` / `SAP_SSO2_ARGS` / `SAP_SSO2_TIMEOUT_MS` in the legacy single-system form (`src/lib/sso2TicketProvider.ts`).
- The authenticated cookie client refuses any request URL that resolves outside its configured SAP origin. abap-adt-api hands the client the path to call, and an absolute URL among them would have overridden `baseURL` and carried the SAP session to another host; the check applies to every cookie mode, so browser `sso` destinations gain it too (`CookieHttpClient.requestUrl`).
- `authType: sso2` refuses a plaintext `http://` destination, and refuses `insecureTls` (or `SAP_TLS_INSECURE`) as well: encryption without verification means the ticket is handed to whatever answers on that name. A destination behind a private certificate authority uses `tls.ca`.
- The legacy `SAP_URL` form is validated at startup like the `systems.json` form. It never ran `validateSystem` at all, so the rules above, the URL check and the `basic` credential check reached the map form only. A single-system configuration that was already invalid now says so at startup instead of failing on the first call.
- A cookie destination no longer reports its auth mode as the SAP user name. The ADT client is constructed with `user` when the destination configures one, and `SSO2` joins `SSO`, `OAUTH` and `BROWSER` as a placeholder that means "no known user". Without this, `activatePackage` on an `sso2` destination filtered the package tree by a SAP user named SSO2, which owns nothing: every object was reported as belonging to someone else and the activation returned success having activated nothing.
- Docs: mode sso2 in `docs/AUTH.md` with the SAP-side notes (`login/create_sso2_ticket`, `login/accept_sso2_ticket`, ICF logon procedure), the configuration keys and variables in `docs/CONFIGURATION.md`, the `insecureTls` rule in `docs/TROUBLESHOOTING.md`, `SECURITY.md`, `.env.example`, `systems.example.json`, `server.json`, and a Collaboration section in the three READMEs.

## [2.6.0] - 2026-09-30 - Table data needs a decision, values as SAP sent them, SAP API Policy page
Two things change what an existing setup gets, and both are deliberate: `tableContents` and `runQuery` are refused until a destination allows them, and table values come back as the strings SAP sent. Both are described first, with the one-line way to keep the old behaviour. The rest is fixes. Everything below was tested live on an S/4HANA 2023 on-premise system and on an S/4HANA Cloud Public Edition tenant.

### Table data, API policy standing, SAP API Policy page
What changes when you upgrade: `tableContents` and `runQuery` are refused on every destination until its policy allows them.
- **Table data is off unless the destination opens it (breaking).** New policy key `allowDataPreview`: `true` lets `tableContents` read the rows of a table or CDS entity by name. `allowFreeSql` changes from "on unless `false`" to "off unless `true`"; `true` allows `runQuery` and `tableContents` with `sqlQuery` and implies `allowDataPreview`, and an explicit `allowDataPreview: false` closes both. The two gates are the only ones that also run on a destination without a `policy` block, which stays fully writable otherwise. Reason: SAP's FAQ on its API Policy (version 1.3, question 33) names reading application tables and running SQL first among the uses ADT is not intended for, and section 2.2.2 of the policy restricts extraction, so reading business data should be a decision, not a default.
- **To keep the behaviour of 2.x**, either state `"allowFreeSql": true` in the `policy` of the destinations that should read data, or start the server with `MCP_ALLOW_FREE_SQL=1`. Both new variables, `MCP_ALLOW_DATA_PREVIEW` and `MCP_ALLOW_FREE_SQL`, set the default for the destinations that do not state the key; a destination that states `false` stays closed whatever the variables say. A policy that states `"allowFreeSql": false` and relied on `tableContents` by name needs `"allowDataPreview": true` next to it.
- The refusal names the key to set and the variable that sets the default, and says when the closure was stated by the destination itself. `listSystems` reports the effective `dataAccess` (`allowDataPreview`, `allowFreeSql`) of every destination, with or without a policy. The descriptions of `tableContents` and `runQuery` and the server instructions tell the model that a refusal is final.
- **`apiReleaseState` reports `apiPolicy`** on every object: `released`, `classic`, `notReleased`, `prohibited`, `customer` or `unknown`. `prohibited` outranks every other state of the same object and is listed apart (`prohibited`, `summary.prohibited`, `prohibitedNote`). It comes from a state or label of the repository that says prohibited, not permitted, unpermitted, forbidden or not allowed, or from the built-in list of interfaces SAP declared not permitted in an SAP Note: today the ODP Data Replication API over RFC (`RODPS_REPL*`, SAP Note 3255746).
- **Ready for the classification SAP announced.** SAP said it will extend the cloudification repository with interfaces that are not released and interfaces that are prohibited; on 2026-09-29 the repository does not carry it yet. Every array of entries of a file is read whatever its key; a state this version does not know is passed through as written, flagged `unrecognizedState`, listed in `unrecognizedStates` and never counted as cloud ready; `MCP_API_CLASSIFICATION_FILES` adds files (a `.json` path inside the repository, such as a partner file, or an `https` URL) without a new release, and a file that cannot be read is reported in `repository.extraFiles` instead of being skipped in silence.
- `apiReleaseState` keeps what the repository says and the server used to drop: `labels` (`remote-enabled`, `transactional-consistent`) and `successorConcept` (a successor given as a concept instead of an object). `notToBeReleased` and `notToBeReleasedStable` are described as what they are.
- New editions `pce` (`objectReleaseInfo_PCELatest.json`) and `pce2025`; `pce2023` reads feature pack 3 (was 2). An unknown `edition` is refused by name instead of failing on an undefined file.
- New [docs/API-POLICY.md](docs/API-POLICY.md): the SAP API Policy v.4.2026a section by section, what SAP has published around `/sap/bc/adt`, what the server does on its side (identity, guard rails, data access, release states, load, audit), the questions only SAP can answer and a conservative configuration. It states plainly what SAP's FAQ says: the ADT APIs are internal, for development through endorsed channels only, and a third-party MCP server is not among the channels listed. Linked from a new "SAP API Policy" section in the three READMEs.
- Docs and examples follow: the policy tables in the three READMEs, `docs/CONFIGURATION.md` (truth table of the two keys, the three variables), `docs/AUTH.md`, `docs/CLOUD.md`, `docs/WORKFLOWS.md`, `docs/TROUBLESHOOTING.md`, `docs/ARCHITECTURE.md`, `SECURITY.md`, `systems.example.json`, `server.json` and the setup skill.

### Four defects inherited from abap-adt-api and from Node's defaults
Each reproduced against the library before it was touched, each fix with a test that failed first. The first one changes the format of an answer.
- **`tableContents` and `runQuery` no longer lose data (breaking).** The values went through abap-adt-api's decoder, which runs every numeric column through `parseFloat` or `parseInt`: `12.34-` (SAP's trailing minus) came back as `12.34`, the NUMC key `000010` as `10`, `1234567890123456.78` as `1234567890123456.8`, and the initial date `00000000` as `null`. The handlers now always ask the library for the raw result and shape it in `src/lib/queryDecode.ts`. By default every value is the string SAP sent, with the sign of a negative number in front (`-12.34`). `decode=true` gives JSON numbers where the number is exact (safe integers, up to 15 significant digits) and the string otherwise, formats a valid date as `YYYY-MM-DD`, keeps the initial date as sent, and never turns NUMC into a number. Whether a given system sends the trailing minus was not checked live; the other three losses do not depend on it.
- **What changes when you upgrade:** without `decode=true`, numeric and date columns are strings, not numbers and ISO timestamps. With `decode=true`, a date is `2026-09-29`, not `2026-09-29T00:00:00.000Z`, and a number that does not fit a double stays a string.
- **`createObject` and `runSnippet` create the object in the logon language of the destination.** Both used the positional `createObject(...)` of the library, which cannot carry a language, so the library wrote `adtcore:language="EN"` and `adtcore:masterLanguage="EN"` whatever `language` the destination had. Order now: the `language` of the call (new optional arguments `language` and `masterLanguage` on `createObject`), the `language` of the destination, then EN as before. A value that is not a two-letter key is refused before anything is sent, since the library copies it into an XML attribute as it is. Packages (DEVC/K) are unchanged: their request carries no language.
- **New error kind `network`.** On cookie destinations (`sso`, `sso2`) a connection that failed or timed out (`ECONNRESET`, `ETIMEDOUT`, `ENOTFOUND`, `ECONNREFUSED`) reached the model as `serverError`, `httpStatus: 500`, with the hint to look for a short dump, because abap-adt-api wraps every error it does not recognise as an exception with `err` 500. The new kind has no HTTP status, names the destination and its host, and says that a failed write may or may not have reached SAP. The wrapper's 500 is no longer taken for a status anywhere: an expired SSO session reported `httpStatus: 500`, and an error thrown inside the client counted as an SAP server error. A 500 that SAP sent is reported as before.
- **Locks are released when the process dies of an error.** Only `SIGINT` and `SIGTERM` were handled; a promise rejected without a handler or an uncaught exception ended the process with exit code 1, every SAP session without a logoff and every lock left in SAP. A rejection without a handler is now reported and the server keeps running; an uncaught exception releases locks and sessions within five seconds and exits with 1 (`src/lib/processGuards.ts`). The report is the message and the first stack lines, redacted, never the error object. No such rejection was found in the server's own code; the guard is for the libraries it runs.
- Not changed, and still open: an ICM error page with `400` and `ICMENOSESSION` is classified `ambiguous400`, which does not log in again. Other clients treat it as a lost session; it was not reproduced on a system, so the rule was left alone.

## [Unreleased]

### RFC transport for on-premise systems below SAP_BASIS 7.51
- **New `"transport": "rfc"` per destination.** SAP_BASIS below 7.51 (SAP ERP 6.0 EHP7 and EHP8 among others) ignores the stateful ADT session over HTTP, so a lock dies with its request and every write failed with 423 `invalid lock handle`. An RFC destination sends each ADT request as one call of `SADT_REST_RFC_ENDPOINT` over a persistent RFC connection, as Eclipse does on-premise, so locks hold and writes work. Tools, policies and hints are unchanged. Two connections per destination by default (`rfc.sessions: "split"`): one holds the locks, the other carries everything else and is reset after each write; `"single"` is the fallback.
- **The SAP NetWeaver RFC SDK is the user's download, never bundled.** SAP's connector licence forbids redistribution, so it is not in the npm package, the repository, the releases or the container image. The server loads it from `rfc.sdkPath` or `SAPNWRFC_HOME` through its own small binding (koffi, an optional dependency with prebuilt binaries; SAP's node-rfc wrapper is archived and not used). Only RFC destinations load it, on first use. New guide `docs/RFC.md`: who needs it, where to download the SDK and which archive to pick, install per platform, configuration, SAP-side prerequisites (gateway port, `S_RFC`, logon tickets) and every error.
- Logon: `basic` (user and password), or `sso`/`sso2`, where the `MYSAPSSO2` ticket of the browser login or the provider becomes the RFC logon. `oauth` is refused for RFC destinations.
- New error kinds `rfcSdkMissing` (with the download link, or the npm setting when koffi was skipped) and `rfcSessionLost` (the connection that held the locks ended; lock again); an unreachable gateway or a dropped request connection is `network`. These rules apply only to RFC destinations, so HTTP classifications are unchanged.
- A refused password logon is reported once, and the destination then makes no further password logon until `login` is called or the server restarts, so failed attempts cannot add up to a locked SAP user; a refused SSO ticket triggers one fresh login, as over HTTP.
- An ABAP message or a short dump in the endpoint ends that connection's session, as the SDK documents: the SAP error is reported, the next call reconnects, and locks lost with it are named.
- The SDK's `dev_rfc.log` and traces go to `~/.abap-adt-mcp/rfc` (mode 0700), and `sapnwrfc.ini` is read only from there, never from the folder the host started in (often the user's project).
- A process that loaded the SDK used to hang on exit (the SDK closes stdout at exit and koffi's exit-time flush then blocks); the server now ends through the C runtime's immediate exit once everything Node runs on exit has run. Only RFC destinations load the SDK.
- `runClass` and `runSnippet` on an RFC destination with the default split sessions keep the locks: the request connection is fresh after every write. With `rfc.sessions: "single"` they end that session for a fresh load and report the released locks.
- `classIncludes` works on SAP_BASIS 7.40, whose class structure links carry no `text/plain` type (the library helper threw `Cannot read properties of undefined (reading 'href')`); the include URL now falls back to the source link and then to `abapsource:sourceUri`.
- `createAtcRun`, `atcCheckVariant`, `atcSummary`, `whereUsed` and `usageReferences` explain a 404 on SAP_BASIS 7.40, which has neither `/sap/bc/adt/atc/worklists` nor `usageReferences` (only older protocols this server does not speak), instead of a bare Not Found. The 404 is read from wherever abap-adt-api puts it (`err`, `status` or `response.status`).
- `runQuery` explains a 404 (no free-style data preview, as on SAP_BASIS 7.40: use `tableContents` with `select * from <table> where ...`), and the data preview hint recognises the 7.40 error for a field list ("explicit length specifications").
- **`setTextElements` could overwrite program source (since 0.3.2).** The handler passed the object URL to abap-adt-api, which appends `/source/<category>` to it, so the tools read and wrote `/sap/bc/adt/programs/programs/<name>/source/symbols` instead of the text element resource `/sap/bc/adt/textelements/programs/<name>`. On SAP_BASIS 7.40 the program resource serves that path as the main source, and a write replaced the program code with the text lines (found in the live test on P03, on a test program in `$TMP`, restored). Both tools now map the object URL to `/sap/bc/adt/textelements/{programs|classes|functiongroups}/<name>` and never touch the object source; a 404 there (no text element resources, as on 7.40) is reported instead of an empty list or a bare Not Found. SAP_BASIS 7.53 (S4D) behaves the same: the old path answers the main source, so released versions could overwrite program source there as well, over HTTP too; 7.53 has no text element resources either (the object links its text elements to SAP GUI).

On P03 this happened for under 90 seconds after all sessions of the user were ended in SM04, and the same ticket then logged on again; the final error now says so and when to call login. SAP activates only unlocked objects, which is why Eclipse unlocks on save.

### Diagnostics
- **`MCP_ADT_TRACE_FILE`** writes one JSON line per ADT request (method, URI, status, headers) for diagnosing a backend that behaves differently. Cookie, Set-Cookie, Authorization and CSRF values are reduced to name and length, no response body is kept (error lines carry the first 300 characters of the redacted error text, and 501 marks a failure without an SAP answer), and the file is created private. Declared in `server.json`.
