# Security policy

abap-adt-mcp gives a language model authenticated access to SAP systems through ADT. That access includes writing source, releasing transports, deleting objects and executing ABAP. This document covers how to report a problem in the server, what the server can do on your behalf, which controls bound that, and which risks remain. It complements [Keeping it safe](README.md#keeping-it-safe) in the README, [docs/CONFIGURATION.md](docs/CONFIGURATION.md) (every option, with recipes) and [docs/AUTH.md](docs/AUTH.md) without repeating them.

## Supported versions

| Version | Supported |
|---|---|
| 0.3.3 (latest release) | Yes |
| 0.3.2 and earlier, including 0.1.x | No |

Only the newest release receives fixes; a fix ships as a new patch release and nothing is backported. `healthcheck` and `GET /health` report the running version. `npx -y abap-adt-mcp` installs whatever npm resolves as the newest release rather than a pinned one; a pinned install (`abap-adt-mcp@0.3.3` or the `vX.Y.Z` container tag) needs a deliberate bump to pick up a fix, so watch the releases and [CHANGELOG.md](CHANGELOG.md).

## Reporting a vulnerability

Report suspected vulnerabilities through GitHub private vulnerability reporting on this repository (Security tab, "Report a vulnerability"). That channel is private: GitHub shows the report to the repository maintainer and does not publish it. Use it, not a public issue, for anything that touches a real system.

The project has no other private channel: no dedicated security email, no PGP key, no `security.txt`. If the Security tab entry is not offered to you, the only fallback is a public GitHub issue that says nothing more than "security, please contact me" (the maintainer, the author named in [package.json](package.json), Willian Saez, will ask you privately from there how to proceed). Because that fallback issue is itself public, do not put any detail in it; wait for the private follow-up. There is no published maximum embargo window, no committed fix SLA beyond "a fix ships in a patch release" (see Supported versions above), and the project does not request CVE identifiers for its own fixes; a GitHub Security Advisory drafted from a report can carry one if the reporter needs it.

A useful report contains the version, the transport (stdio or HTTP), the destination `authType` and `policy` block with hostnames and secrets removed, the tool and arguments involved, and what the server returned. Placeholders (`ZCL_EXAMPLE`, `DEVK900123`, `https://sap.example.com`) are welcome; real tenant hostnames, customer names and transport numbers are best left out.

What to expect: an acknowledgement within a few days, an assessment of whether the problem is in this server, in [abap-adt-api](https://www.npmjs.com/package/abap-adt-api), in the MCP SDK or in SAP, and a fix in a patch release with a CHANGELOG entry that describes the class of problem without a working exploit. Credit is given on request. Problems in SAP products belong to SAP's disclosure process; problems in a host (Claude Desktop, Claude Code, Eclipse) belong to that host's vendor.

## Threat model

### What the server can do on SAP

The server acts as the SAP user (or Communication User, or OAuth client) configured for each destination, with exactly that user's authorizations. Nothing in the server escalates them, and nothing reduces them except the policy layer below. From a security standpoint the tools in [docs/TOOLS.md](docs/TOOLS.md) fall into four classes:

- **Reads** of metadata, source, data and runtime information: `getObjectSource`, `tableContents`, `runQuery`, `dumps`, `usageReferences`, `exportPackageSources` (which copies whole package trees to local disk) and every tool annotated read-only.
- **Writes** to the repository: `createObject`, `setObjectSource`, `editObjectSource`, `setMethodSource`, `deleteObject`, `atcApplyQuickfix`, `renameExecute`, `changePackageExecute`, `setTextElements`, `setDomainProperties`, `setDataElementProperties`, `gitPullRepo`, `pushRepo`, `rapGenGenerate`, `publishServiceBinding`, activation and lock tools.
- **Transport lifecycle**: `createTransport`, `resolveTransport` with `createIfMissing=true`, `transportRelease`, `transportDelete`, `transportSetOwner`, `transportAddUser`. Releasing a transport moves code towards production and cannot be undone by the server.
- **Code execution**: `runSnippet` wraps arbitrary ABAP in a temporary `IF_OO_ADT_CLASSRUN` class (in `packageName`, default `$TMP`), activates it, runs it and deletes it again unless `keep=true`; `runClass` runs an existing class; `unitTestRun` executes test code; the debugger toolset can change variable values in a running session (`debuggerSetVariableValue`). Executed ABAP runs with the connected user's full authorizations, including any database update that user may perform.

The set of tools the server marks `destructiveHint` is `DESTRUCTIVE_TOOLS` in [src/toolManifest.ts](src/toolManifest.ts); `READ_ONLY_TOOLS` in the same file is what `readOnlyHint` and the `readOnly` policy key mean. Those annotations are advice to the host; the host may ignore them.

### Who the attacker is

Three actors matter:

1. **The model, steered by content it reads.** Source comments, table rows, ATC finding texts, dump feeds and abapGit remotes are all inputs the model sees. A string in any of them can ask the model to release a transport or delete a class. See [Prompt injection](#prompt-injection).
2. **A local or network caller that reaches the MCP endpoint.** On stdio the caller is whoever can start the process. On HTTP the caller is whoever holds the bearer token and can reach the bind address. See [HTTP transport hardening](#http-transport-hardening).
3. **A reader of local files or the process environment**: `systems.json`, `.env`, the audit file, the SSO profile directory, `docker inspect`. See [Secrets handling](#secrets-handling) and [Local files written](#local-files-written).

A fourth actor is not modeled: **the MCP host itself.** The host holds the bearer token (HTTP) or spawns the process directly (stdio), and every tool result, including source code and business data, passes through its transcript and logging before the model or the person sees it. This document assumes the host is trustworthy; nothing in the server verifies or bounds it.

The SAP system itself is trusted for the authenticity of its answers over TLS, not for the safety of their content.

### The policy layer

Every tool call on a destination that has a `policy` block passes `evaluatePolicy` in [src/lib/policy.ts](src/lib/policy.ts) inside the per-destination queue of the dispatcher in [src/index.ts](src/index.ts), before login and before the tool's own SAP request. The one gate that may itself talk to SAP is `allowedPackages`: to learn the package of an existing object it logs in and calls `transportInfo` (a read), then decides; a package that was found is cached per destination and per object URI (a lookup that comes back empty is not cached), and the cache is cleared after `createObject`, `deleteObject`, `renameExecute`, `changePackageExecute`, `gitPullRepo` or `rapGenGenerate`, so a repeated denied write against the *same* object whose package did resolve is served from cache, but a script that tries many *different* objects at a closed `allowedPackages` destination still costs one login and one `transportInfo` call per new object, all serialized one at a time by the destination's own queue, and each attempt is captured in the audit log with `outcome: "denied"`. This evaluation is the guarantee the server makes regardless of what the host approves. A refusal comes back as a tool error with `kind: "policyDenied"`, a message naming the gate, and `isError: true`; retrying does not help, and the audit record marks it `outcome: "denied"` with the gate in `gate`.

The six keys (`readOnly`, `deniedTools`, `allowFreeSql`, `deniedTables`, `allowedPackages`, `allowedTransports`) are documented key by key in [README: Keeping it safe](README.md#keeping-it-safe) and in depth, with recipes, in [docs/CONFIGURATION.md](docs/CONFIGURATION.md#3-policy-in-depth). What matters for a threat model:

- Gates run in the order listed above and the first refusal wins; a call that passes every gate reaches the handler.
- `readOnly` allows exactly `READ_ONLY_TOOLS` plus `login`, `logout`, `dropSession`, `listSystems`, `healthcheck`, `systemProfile` and `exportPackageSources` (local writes only). `runQuery` and `tableContents` are reads and stay allowed; deny them with `allowFreeSql: false` or `deniedTools` where data must not leave SAP. Everything else, including `createAtcRun`, `atcSummary`, `unitTestRun`, `lock` and the code-execution tools below, is outside `READ_ONLY_TOOLS` in [src/toolManifest.ts](src/toolManifest.ts) and is refused under `readOnly`, whatever the tool itself does; `atcSummary` reads an existing worklist but is refused for the same reason `createAtcRun` is, because the two are not distinguished by the tool list.
- `deniedTables` is matched against the `ddicEntityName` of `tableContents`, every `FROM`/`JOIN` target of any `sqlQuery` argument, and, best effort, the same targets in the ABAP text of `runSnippet` (`code`), `setObjectSource` and `setMethodSource` (`source`). `editObjectSource` replacements are not scanned.
- `allowedPackages` is a closed list: a write whose package cannot be determined is refused. The package lookup is memoised per destination and cleared after `createObject`, `deleteObject`, `renameExecute`, `changePackageExecute`, `gitPullRepo` or `rapGenGenerate`. `gitPullRepo`, `rapGenGenerate`, `rapGenPublishService`, `publishServiceBinding` and `unPublishServiceBinding` cannot derive a package and are always refused under this gate. Reads and navigation are not gated; `lock` and `changePackagePreview` are, because they name a target object.
- `allowedTransports` checks the `transport` or `transportNumber` argument of the write and transport-lifecycle tools that take one (the transport reads `transportDetails` and `transportUnifiedDiff` are not gated) and refuses `createTransport` and `resolveTransport(createIfMissing=true)`, so the model can only use transports an administrator listed.

`MCP_READ_ONLY=1` adds `readOnly` to every destination on top of its own block. A destination without a `policy` block is fully writable within the SAP user's authorizations. `MCP_TOOLSETS` and `MCP_DISABLED_TOOLSETS` hide whole toolsets server-wide; a hidden tool called by name is refused with the toolset name. The platform gate (`MCP_PROFILE_GATE`) refuses tools the backend does not expose; it is a correctness feature, not a security boundary.

A production destination that must never be written to is therefore configured as `{"readOnly": true, "allowFreeSql": false, "deniedTables": [...], "deniedTools": ["exportPackageSources"]}`; a development destination is bounded with `allowedPackages` and `allowedTransports`. Worked examples are in [docs/AUTH.md](docs/AUTH.md#per-destination-policy-server-side-guard-rails) and [docs/CONFIGURATION.md](docs/CONFIGURATION.md#recipes).

## Secrets handling

**Configuration.** Any string in `systems.json` (or `SAP_SYSTEMS`) may be `${env:VAR}`; the loader in [src/lib/systems.ts](src/lib/systems.ts) resolves it at startup and a missing variable fails by name, never by value. On POSIX systems a group- or world-readable configuration file is warned about, and refused outright (`checkConfigFileMode`) only when it holds an inline `password`, `oauth.clientSecret` or `gitPassword`; the check applies to the file named by `SAP_SYSTEMS_FILE` or found next to the package, not to inline `SAP_SYSTEMS`. It does not look at `tls.passphrase` or at inline PEM content in `tls.cert`/`tls.key`/`tls.pfx`: a world-readable `systems.json` carrying an inline private key or client-certificate passphrase gets only the same permissions warning, not a refusal. Use `${env:VAR}` (supported for the passphrase, and for any string value) or a separate file path for `cert`/`key` when the configuration file itself cannot be kept at mode `0600`. `systems.json` and `.env` are excluded from git by [.gitignore](.gitignore); `systems.json`, `.env`, `.env.*`, `*.pem` and `*.key` are excluded from the container image by [.dockerignore](.dockerignore). Certificate and key files are not git-ignored: keep them outside the repository or add your own ignore rule. The legacy single-system variables (`SAP_PASSWORD`, `SAP_OAUTH_CLIENT_SECRET`) and `MCP_HTTP_TOKEN` are environment only.

**What never enters the model context.** The tool schemas offer no way to read configuration: `listSystems` returns destination name, URL, client, `authType`, the policy summary, a one-line TLS description (`custom CA`, `client certificate`, `verification disabled`) and, once known, the platform and unavailable toolsets, never material or passwords; `healthcheck` returns version, destination names, active toolsets and the tool count. Specifically:

- `password`, `oauth.clientSecret`, `tls.passphrase` and `MCP_HTTP_TOKEN` are used by the process and never serialised into a tool result.
- The OAuth access token is held in a closure in [src/lib/oauth.ts](src/lib/oauth.ts), refreshed a minute before expiry and invalidated when SAP answers 401 (the next call fetches a fresh one); it is not returned by any tool.
- SSO session cookies are harvested from the login browser over the DevTools protocol, kept in the in-memory jar of [src/lib/cookieHttpClient.ts](src/lib/cookieHttpClient.ts), and neither written to disk by the server nor returned. The `login` tool takes no arguments.
- `gitUser`/`gitPassword` from the destination are backfilled by [src/handlers/GitHandlers.ts](src/handlers/GitHandlers.ts) when the git tools are called without `user`/`password`, so a remote token can stay in the configuration. The schemas still accept those arguments for compatibility; a token the model is given in the conversation is in the host's transcript, so prefer the configuration.
- `reentranceTicket` returns a live SAP logon credential into the conversation. It is refused unless the server was started with `SAP_ALLOW_REENTRANCE_TICKET=1`; nothing else in the server needs it.

**Redaction, and what it does not cover.** `redactSecrets` in [src/index.ts](src/index.ts) masks `Authorization` header values, `Cookie`/`Set-Cookie` values, `password`/`passwd`/`client_secret`/`sap-password` key-value pairs and `user:password@host` URLs. It runs on exactly two paths: every error message returned to the host (both a tool error and the server's own internal errors), and, separately, the audit log's summary of call arguments, which additionally replaces any argument whose key contains `pass` (so `password` and `passphrase`), `secret`, `token`, `authorization`, `cookie` or `lockHandle` with `[REDACTED]` ([src/lib/audit.ts](src/lib/audit.ts)). A **successful** tool result is not passed through `redactSecrets` at all: it goes straight from the SAP response to the host. Ordinary content from SAP is not expected to contain credentials, but nothing stops a short dump, a trace record, a table row or a text element from echoing a header, a cookie or a connection string that was itself embedded there by something upstream; if it does, it reaches the host transcript unmasked. The server's own diagnostics (the `console.error` lines it writes to stderr) do not pass through `redactSecrets` either: they name destinations, file paths and upstream error text, and the generated bearer token is reported by path rather than by value. Redaction of the two paths it does cover is pattern based and protects against upstream libraries echoing request headers; it is not a guarantee that a credential embedded in an unexpected shape is caught.

## Network

The server opens outbound connections to exactly these places:

| Destination | When | Client |
|---|---|---|
| The configured SAP hosts (`url` of each destination) | Every tool call | `abap-adt-api` over axios, with the destination's `tls` agent |
| The OAuth token endpoint (`oauth.tokenUrl`) | `authType: "oauth"`, on first use and near expiry | Node's built-in `fetch` (system trust store; the destination's `tls` block does not apply to this request) |
| The identity provider | `authType: "sso"`, during login | The Chromium-based browser the server launches (Chrome, Edge, Brave or `SAP_BROWSER_PATH`), not the server process; the server only reads the resulting cookies for the SAP host |
| `raw.githubusercontent.com/SAP/abap-atc-cr-cv-s4hc` | `apiReleaseState`, at most once per file per 24 hours | Node's built-in `fetch`, 15-second timeout, disk cache under `~/.abap-adt-mcp/cache`; a cached copy is used when the download fails |
| Whatever remote URL the git tools are given | `gitExternalRepoInfo`, `gitCreateRepo`, `gitPullRepo`, `pushRepo` | The SAP system's abapGit, not the server |

Because the OAuth token request in [src/lib/oauth.ts](src/lib/oauth.ts) uses Node's global `fetch` rather than the destination's `https.Agent`, the destination's `tls` block (custom `ca`, client certificate) does not apply to it; a token endpoint behind a corporate CA needs that CA in Node's own trust store. The server offers no dedicated option for this. Node's built-in `NODE_EXTRA_CA_CERTS=<path-to-pem>` environment variable, honoured by Node itself rather than by anything in this codebase, is the supported way to add a CA to the system trust store the token request uses; `NODE_TLS_REJECT_UNAUTHORIZED=0` is not an alternative: the server removes it at startup, as described under [TLS](#tls).

`apiReleaseState`'s download carries no hash or signature check beyond the HTTPS connection itself: the response is trusted because the channel is trusted, and the downloaded JSON is cached to disk for 24 hours once fetched ([src/lib/apiReleases.ts](src/lib/apiReleases.ts)). A response tampered with in transit would be caught by TLS; a response served correctly over TLS by a compromised or renamed upstream repository would not be, and would shape `apiReleaseState`'s cloud-readiness verdicts for up to a day before the cache expires.

Install-time traffic is `npm`/`npx` to the npm registry and `docker pull` from GHCR. There is no telemetry, no update check, no crash reporting and no other outbound connection. Inbound, the server listens on nothing unless `MCP_HTTP_PORT` is set.

## HTTP transport hardening

Stdio is the default: one process per user, nothing on the network. `MCP_HTTP_PORT` enables the Streamable HTTP front door in [src/lib/httpTransport.ts](src/lib/httpTransport.ts), described operationally in [README: HTTP transport](README.md#http-transport-optional) and [docs/CONFIGURATION.md](docs/CONFIGURATION.md#6-http-transport). The controls it applies, in request order:

- **Loopback bind** by default (`MCP_HTTP_HOST=127.0.0.1`); ports below 1024 are refused. Binding elsewhere prints a startup warning.
- **`GET /health`** is the only unauthenticated route and discloses version, session count, the session cap and uptime; everything else outside `/mcp` is `404`.
- **Host and Origin validation** against DNS rebinding: on a loopback bind only loopback `Host` values pass (a request without `Host` is refused) unless listed in `MCP_HTTP_ALLOWED_HOSTS`; on a non-loopback bind every `Host` passes, trading that protection away in favour of whatever sits in front of the server (a reverse proxy, a firewall rule limiting who can reach the port). An `Origin` header (browser callers) must be loopback on a loopback bind or listed in `MCP_HTTP_ALLOWED_ORIGINS` (`*` allows any) on either bind; requests without `Origin` pass on either bind.
- **Bearer token** on every request to `/mcp`, compared in constant time on UTF-8 bytes (`bearerOk`). Without `MCP_HTTP_TOKEN` the server generates a fresh 32-byte (256-bit) random token with `crypto.randomBytes` on **every** start and overwrites `~/.abap-adt-mcp/http-token` (mode `0600`) with it, so a plain restart already rotates the token with no extra step; nothing needs deleting first. When you set `MCP_HTTP_TOKEN` yourself, the server does not check its length or entropy, so a short or guessable value is accepted as readily as a strong one; choose one at least as strong as the generated default (32+ random bytes) if you set it explicitly.
- **Session caps and TTL**: at `MCP_HTTP_MAX_SESSIONS` (default 16) further `initialize` requests get `503` with `Retry-After`; `MCP_HTTP_SESSION_TTL_MINUTES` (default 30) of idleness closes a session. Only `initialize` may open a session; only that request path (no `mcp-session-id` header yet) is checked against a fixed 4 MB body cap in the server's own code ([src/lib/httpTransport.ts](src/lib/httpTransport.ts); there is no environment variable to change it), and unknown session ids get `404`. Requests that carry an established `mcp-session-id` are handed directly to the MCP SDK's `StreamableHTTPServerTransport`, which in the pinned SDK version parses the body with no size limit of its own, so those requests are bounded by nothing in this server.
- **Per-session isolation**: every MCP session gets its own `AbapAdtServer` instance, hence its own SAP sessions, lock ledger ([src/lib/lockLedger.ts](src/lib/lockLedger.ts)), source cache ([src/lib/sourceCache.ts](src/lib/sourceCache.ts)) and package memo. Closing or expiring a session releases the locks and SAP sessions that instance holds. `SIGINT`/`SIGTERM` do not: in HTTP mode the handler closes only the listening instance, which holds no SAP session of its own, so locks held by a live session are left to SAP's own session timeout unless the client sends `DELETE /mcp` first ([docs/CONFIGURATION.md](docs/CONFIGURATION.md#session-model)).

**Rejections are silent to the operator.** A failed bearer token, a rejected `Host`/`Origin`, and a session-cap `503` are all handled before the request reaches the MCP dispatcher: none of them writes a `console.error` line, and none is recorded in the audit log (the audit log is written per MCP tool call, which these requests never become). Combined with the lack of any built-in rate limiting, a script probing the token or hammering `/initialize` leaves no trace in anything this server writes; only a reverse proxy or firewall placed in front of it, or an OS-level connection log, would show the attempts. This is worth watching for on any non-loopback bind.

What the transport does not provide, and what you have to add in front of it: TLS termination (use a reverse proxy, see [docs/CONFIGURATION.md](docs/CONFIGURATION.md#reverse-proxy-with-tls)), rate limiting, per-user tokens, an access log with caller identity or with rejected requests. The audit log records no remote address or session id. An SSO destination exposed over a non-loopback bind means every remote caller acts with the browser login of the user who started the server; the server warns about this at startup, and the safe configuration for a shared instance is `basic` or `oauth` destinations, each with a `policy` block, one instance per person where attribution matters.

## TLS

TLS material is configured per destination in the `tls` block ([src/lib/tls.ts](src/lib/tls.ts), [docs/AUTH.md](docs/AUTH.md#tls-custom-ca-and-client-certificates)): `ca` for a corporate or self-signed CA with verification kept on, `cert` + `key` or `pfx` + `passphrase` for X.509 client authentication. Values are file paths or inline PEM, and `${env:VAR}` works for the passphrase. The resulting `https.Agent` is attached to that destination's ADT client only; it does not cover the OAuth token request (see [Network](#network)) or the GitHub download, which use Node's own trust store.

`insecureTls: true` (or `SAP_TLS_INSECURE=1` in legacy single-system mode) sets `rejectUnauthorized: false` on that one destination's agent, and the server prints a warning naming the destinations at startup. It is meant for sandboxes; a CA bundle is the right fix. `NODE_TLS_REJECT_UNAUTHORIZED=0` cannot be used to widen that hole. Node reads it at connection time and it would disable certificate verification for every connection of the process, including destinations that never asked, the OAuth token request and the GitHub download, so `enforceTlsVerification()` in [src/lib/tls.ts](src/lib/tls.ts) deletes it from the environment before the first connection and the server reports that it was ignored. Verification off is a per-destination decision, and it has to name the destination. The SSO login browser manages its own trust store and is not affected by any of these settings.

## Supply chain

- **Releases** are tag driven ([.github/workflows/release.yml](.github/workflows/release.yml)): the workflow checks that the tag, `package.json` and `server.json` agree, runs `npm ci`, the build, the type-check of tests, the test suite and the generated-docs staleness check, verifies that no compiled tests ship, then publishes with `npm publish --provenance` through npm trusted publishing. GitHub OIDC (`id-token: write`) is exchanged for a short-lived publish credential; no long-lived npm token exists in the repository secrets. Verify an installed copy with `npm audit signatures`.
- **Container images** are built in the same workflow from [Dockerfile](Dockerfile) (`node:22-alpine`, `npm ci`, `npm prune --omit=dev`, unprivileged `node` user) and pushed to `ghcr.io/williansaez/abap-adt-mcp` as `latest` and `vX.Y.Z`. Tags are mutable by nature; pin by digest for a controlled rollout. Hardening stops at the unprivileged user: the image is not built or run with a read-only root filesystem, dropped Linux capabilities, an image signature (no cosign step in the workflow) or a resource limit; add those at the container-runtime or orchestrator level (`docker run --read-only --cap-drop=ALL --memory=... --pids-limit=...` or the equivalent Kubernetes `securityContext`/`resources`) if you need them, since the image does not set them for you. Anything the process writes under `~/.abap-adt-mcp` (the token file, the release-state cache, exports, the audit log) lands in the container's writable layer unless you mount a volume there; without one it is lost when the container is removed.
- **Dependencies** are declared with caret ranges in `package.json` (`@modelcontextprotocol/sdk`, `abap-adt-api`, `axios`, `diff`, `dotenv`, `puppeteer-core`) and pinned by the committed `package-lock.json`, which CI and the image build honour through `npm ci`. Consumers installing with `npx` resolve the ranges at install time; pin the package version to control that. `puppeteer-core` drives an existing Chromium on the workstation and downloads no browser. There is no Dependabot or Renovate configuration in this repository, no `npm audit` step in CI, no generated SBOM and no image-signing step: dependency vulnerabilities are caught, if at all, by whoever runs `npm audit` locally or by GitHub's own Dependency Graph / Security Advisories for the repository, not by anything this project runs on your behalf. Run `npm audit` yourself before an update, or add your own scanning in a fork or downstream pipeline.
- **CI** ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs the suite on Node 18, 20 and 22, builds the image and checks that it starts and lists tools. Security-relevant units have their own tests: `policy.test.ts`, `systems.test.ts`, `httpTransport.test.ts`, `audit.test.ts`, `tls.test.ts`, `cookieHttpClient.test.ts`, `lockLedger.test.ts` and `sourceCache.test.ts`.

## Local files written

Everything the server writes lives under `~/.abap-adt-mcp` unless an option relocates it. The directory itself is created with mode `0700` the first time any of these is needed.

| Path | Written by | Mode | Contents |
|---|---|---|---|
| `sso/<host>/` | Browser SSO login ([src/lib/browserLogin.ts](src/lib/browserLogin.ts)) | `0700` | A dedicated Chromium user-data directory: the identity provider's "stay signed in" cookies and local storage, managed by the browser under its own rules. The server itself writes no cookie anywhere. `SAP_BROWSER_PROFILE_DIR` moves this directory elsewhere; that directory is created with the process umask, not `0700`, and a value equal to Chrome's default profile directory is rejected on purpose (the check knows the macOS path only). |
| `http-token` | HTTP transport when `MCP_HTTP_TOKEN` is unset | `0600` | The generated bearer token, rewritten on every start (see [HTTP transport hardening](#http-transport-hardening)). |
| `cache/` (`MCP_CACHE_DIR` overrides) | `apiReleaseState` ([src/lib/apiReleases.ts](src/lib/apiReleases.ts)) | dir `0700`, files `0600` | Public JSON files from SAP's cloudification repository; no customer data. |
| `exports/` (`MCP_EXPORT_ROOT` overrides) | `exportPackageSources` ([src/lib/abapgitExport.ts](src/lib/abapgitExport.ts)) | root `0700`; sub-directories and files follow the process umask | Your ABAP source in abapGit layout plus an `EXPORT.json` manifest. The target must be absolute and inside the root, compared on real paths so a symlink cannot escape; existing files are not overwritten unless `overwrite=true`. There is no size cap or quota on how much a single export, or repeated exports, can write: the tool copies whatever the package contains. On a `readOnly` destination this tool stays allowed (it performs no SAP write), so a caller who can reach it, including a remote HTTP caller with nothing more than the bearer token, can still fill the server host's disk with ABAP source one package at a time; bound this with an OS-level disk quota on `MCP_EXPORT_ROOT`, or add `exportPackageSources` to `deniedTools` on any destination reachable by callers you do not fully trust. |
| `MCP_AUDIT_FILE` (anywhere) | Audit log ([src/lib/audit.ts](src/lib/audit.ts)) | dir `0700`, file `0600` | One JSONL record per call; see [README: Audit log](README.md#audit-log) and [docs/CONFIGURATION.md](docs/CONFIGURATION.md#7-audit-log-record-format). Argument strings up to 200 characters are kept after redaction, so SQL literals and short snippets are in the file. Records are appended with `fs.appendFileSync` and nothing else: there is no append-only enforcement beyond the file mode, no hash chain and no built-in shipping to a SIEM. On a shared HTTP instance the records also carry no caller identity (see [HTTP transport hardening](#http-transport-hardening)), so treat the file as a local, mutable log to forward and protect with your own tooling, not a tamper-evident record. |

Nothing else is written. `dotenv` reads a `.env` file next to the installed package at startup if one exists; that file is a configuration input, not something the server creates. Note that the export directory and the audit file contain source and call history that may be confidential in your organisation: back them up, rotate them and delete them under the same rules as the SAP data they came from.

**The SSO cookie harvest, more precisely.** `browserLogin` in [src/lib/browserLogin.ts](src/lib/browserLogin.ts) launches Chromium through `puppeteer-core` without `pipe: true`, so the launcher's default applies: Chrome is started with `--remote-debugging-port=0`, an OS-assigned ephemeral TCP port (Chrome binds it to loopback unless told otherwise), not a named pipe. `puppeteer-core` reads the resulting `ws://` endpoint from the browser process's own stderr, not from a file; Chrome also writes that port into a `DevToolsActivePort` file inside the profile directory, which is the same `sso/<host>/` (or `SAP_BROWSER_PROFILE_DIR`) directory this table describes, and on the default path that directory is `0700`, so another OS user cannot read the port number from it. The DevTools protocol itself carries no further authentication beyond knowing the port and the WebSocket path, so for the duration of the login window (`opts.timeoutMs`, five minutes by default) another process running as the **same** OS user, one that can read that file or otherwise find the port, could in principle attach to the same debugging session and read the cookies the login produces. This is the standard trust boundary of local Chrome DevTools automation, not something specific to this server, and it does not extend to other OS users or to the network.

## Prompt injection

Every tool result is data that came from SAP, and SAP content is written by people and by other systems: a class comment, a customer name in a table row, an ATC finding text, a short dump, a text element, a commit message pulled through abapGit. Any of them can contain text that instructs the model to do something else. The server does not filter, rewrite or sandbox tool results, and it cannot tell a legitimate instruction from an injected one.

The consequences of this design:

- **Host approvals are not the boundary.** Tool annotations (`readOnlyHint`, `destructiveHint`) advise the host, and a host may auto-approve. The boundary is the destination `policy`, evaluated in the server before every handler runs. Configure it as if the model will eventually be asked, by content it read, to do the worst thing the configuration allows.
- **Read-only means read-only for SAP, not for the network.** A `readOnly` destination still answers `runQuery`, `tableContents` and `exportPackageSources`, and the model can carry what it read into the next tool call on another destination or into the conversation. Deny those tools where the data or the source must not leave the system.
- **Prompts and skills are static.** The six built-in prompts in [src/prompts.ts](src/prompts.ts) and the skills under [skills/](skills/) are text shipped with the repository; they fetch nothing at runtime.
- **Review destructive calls.** Use a host that shows tool calls before running them and read `deleteObject`, `transportRelease`, `transportDelete`, `setObjectSource`, `editObjectSource`, `setMethodSource`, `pushRepo`, `runSnippet`, `runClass` and `forceUnlock` before approving. `objectDiff` and `transportUnifiedDiff` show what changed, which is the honest way to check a write after the fact; [docs/WORKFLOWS.md](docs/WORKFLOWS.md#3-changing-code-safely) describes the review loop.
- **Injected content can also ride an unmasked tool result back to the host.** As noted in [Secrets handling](#secrets-handling), only error messages and audit summaries pass through `redactSecrets`; a successful result is not screened for anything, injected instructions or otherwise.

## Residual risks

What the controls above do not cover:

- **Executed ABAP is opaque to the policy.** `runSnippet` and `runClass` run code with the connected user's authorizations. `deniedTables` scans the snippet text for `FROM`/`JOIN` targets, and `allowedPackages`/`allowedTransports` bound where the temporary class lives, but dynamic SQL, CDS views over a denied table, function modules, and any update the code performs are not inspected. On a system where code execution is unacceptable, list `runSnippet`, `runClass` and `unitTestRun` in `deniedTools` or use `readOnly`, and connect with a user that lacks `S_DEVELOP`.
- **`deniedTables` is best effort.** Views, joins hidden behind CDS, dynamic table names and `tableContents` on a view over a denied table are not detected. Real data protection is the SAP display authorization of the connected user.
- **`allowedPackages` depends on a lookup.** An object's package is resolved through `transportInfo`; when SAP does not answer, the write is refused (fail closed), which can block legitimate work rather than allow illegitimate work.
- **One credential per destination.** All callers of a server instance share the configured SAP identity; SAP's change documents show that user, not the person behind the model. Attribution needs one instance per person, or an audit file per instance.
- **A shared HTTP instance is a shared secret.** One bearer token, no per-user tokens, no TLS, no rate limiting in the server itself, and no logging of the failed attempts that limiting would normally catch (see [HTTP transport hardening](#http-transport-hardening)). An SSO destination on a shared instance hands the launching user's browser session to every caller.
- **`exportPackageSources` has no output quota.** It is one of the tools a `readOnly` destination still allows, and nothing bounds how much it can write to `MCP_EXPORT_ROOT`; see [Local files written](#local-files-written).
- **Local state is protected by file permissions only.** The SSO profile directory holds an identity-provider session that the server does not encrypt; the audit file and the export root hold source, SQL literals and call history in plain text. Deleting the SSO directory is the only way to end that session early from the workstation; see [Decommissioning](#decommissioning) for what else that leaves outstanding.
- **Environment variables are visible to the process tree** and to `docker inspect`; `MCP_HTTP_TOKEN` and `${env:VAR}` secrets are as safe as the environment that carries them.
- **The host keeps its own transcript.** Everything a tool returns, including business data and anything the model was tricked into echoing, lands in the host's conversation and log files, outside the server's control. The threat model above does not treat the host itself as untrusted; a compromised or careless host inherits everything the bearer token or the running process could do.
- **Redaction is pattern based, and does not cover successful tool results at all.** A secret in an unusual format inside an upstream error message may pass through the two paths it does cover; see [Secrets handling](#secrets-handling).
- **Tools stay listed when denied.** `deniedTools` and the platform gate refuse at call time; a model may still attempt the call, which costs a round trip and an audit record, nothing more.
- **`GET /health` is public** on whatever address the HTTP transport binds to; block it at the proxy if version disclosure matters.
- **Dependency and image supply chain rely on external tooling.** No Dependabot/Renovate, no `npm audit` in CI, no SBOM, no image signing ship with this project; see [Supply chain](#supply-chain).
- **`apiReleaseState`'s upstream JSON is trusted by TLS alone,** with no additional hash or signature check and a 24-hour cache; see [Network](#network).
- **Upstream code paths.** ADT parsing, cookie handling and the browser automation come from `abap-adt-api`, `axios` and `puppeteer-core`; a vulnerability there is a vulnerability here until the dependency is bumped in a new release.

## Decommissioning

When a workstation running this server is lost, retired or suspected compromised, or a token is suspected leaked, there is no single "revoke everything" switch; the server holds several independent pieces of local and remote state, and each is closed differently:

- **HTTP bearer token.** Restarting the server without `MCP_HTTP_TOKEN` set already generates and writes a new one (see [HTTP transport hardening](#http-transport-hardening)); if you set the token explicitly, change it and restart. Delete `~/.abap-adt-mcp/http-token` if you want no trace of the old value on disk, though a restart overwrites it regardless.
- **SSO browser session.** Delete `sso/<host>/` (or the directory named by `SAP_BROWSER_PROFILE_DIR`) under `~/.abap-adt-mcp`. This removes the local copy of the identity provider's "stay signed in" cookies but does not revoke the session at the identity provider itself; if the workstation may have been read by someone else before you deleted the directory, also end that session (log out, or revoke it) at the identity provider's own session management, which this server has no way to reach.
- **OAuth client credentials.** `client_credentials` tokens are short-lived and cached only in memory (see [Secrets handling](#secrets-handling)), but the long-lived `clientSecret` in `systems.json`/environment is not: if it may have leaked, rotate it in the SAP Communication Arrangement (or equivalent OAuth client registration) on the SAP side, not just in the local configuration.
- **Basic-auth password.** Change the SAP user's password; the server has no cached copy beyond what is in `systems.json`/environment for the current process.
- **Local files.** Delete or archive `~/.abap-adt-mcp` (`http-token`, `cache/`, `exports/`) and any `MCP_AUDIT_FILE`, `systems.json` and `.env` per your organisation's data-handling rules for the SAP data and credentials they may contain (see [Local files written](#local-files-written)).
- **Reverse proxy / firewall.** If a non-loopback HTTP deployment was in play, remove or rotate whatever the front-end proxy used to authenticate or authorize the request (its own credentials, IP allow-lists), independently of the steps above.

The mitigations are always the same three: a `policy` block on every destination, a SAP user with only the authorizations the task needs, and a host that asks before it writes.
